# Jupa Mainnet Security Review — 2026-10-14

- Mode: Daily, scoped to contracts, deployment, signer handling, and settlement indexing
- Confidence gate: 8/10
- Target: Arc mainnet (chain ID 5042)

## Stack summary

Jupa is a pnpm TypeScript monorepo with a Next.js checkout, Postgres/Drizzle
state, a Viem indexer, and Solidity 0.8.28 settlement contracts deployed with
Foundry. Circle App Kit/CCTP routes USDC to deterministic Arc receivers.

## Resolved during this review

### [CRITICAL] JUPA-001: Counterfactual receiver could be consumed with dust

**Confidence:** 10/10
**Category:** Insecure design / STRIDE denial of service
**Location:** `contracts/src/CrosschainPaymentFactory.sol`

An attacker could pre-fund a predicted receiver with dust and call `settle`,
permanently deploying the one-shot receiver before the real CCTP mint. Later
USDC would remain trapped at the deployed address.

**Remediation applied:** receivers are persistent and factory-only sweepable.
Subsequent CCTP mints can be swept safely. Tests cover repeat sweeps and reject
direct unauthorized sweeps.

### [HIGH] JUPA-002: Replayed/partial settlement events were not safely aggregated

**Confidence:** 10/10
**Category:** Software/data integrity
**Location:** `apps/indexer/src/index.ts`, `packages/db/src/schema.ts`

The old one-row/on-conflict-ignore model could not credit a legitimate payment
after an earlier dust settlement and lacked event-level replay deduplication.

**Remediation applied:** each Arc log is deduplicated by transaction hash and
log index, while payment totals are accumulated transactionally.

### [HIGH] JUPA-003: Deployment scripts consumed a raw environment private key

**Confidence:** 10/10
**Category:** Cryptographic key management
**Location:** `contracts/script/Deploy.s.sol`, `DeployCrosschain.s.sol`

**Remediation applied:** deployment scripts now use Foundry's broadcast signer,
allowing an encrypted keystore via `--account`. A guarded combined mainnet
script verifies chain ID, canonical USDC bytecode, and role separation.

### [HIGH] JUPA-004: Direct Drizzle ORM advisory

**Confidence:** 9/10
**Category:** Software supply chain

**Remediation applied:** upgraded `drizzle-orm` from 0.44.7 to 0.45.4.

### [HIGH] JUPA-005: Admin and relayer shared one hot EOA

**Confidence:** 10/10
**Category:** Broken access control / STRIDE elevation of privilege

**Remediation applied:** the mainnet registry was deployed with separate roles:
admin `0x60646C2Ec7623D365575850583f7A74BB44c69db` and relayer
`0x2e5d8B56F9B4770a88794a47C32c177542d2f6ea`. On-chain role state was
verified after deployment.

## Open findings blocking full production cutover

### [HIGH] JUPA-006: Runtime services still load a raw relayer key

**Confidence:** 10/10
**Category:** Cryptographic key management
**Location:** `apps/indexer/src/index.ts`, `apps/web/src/lib/registry.ts`

The web service and indexer load `RELAYER_PRIVATE_KEY`. Production should use a
managed signer/KMS or Circle developer-controlled wallet with restrictive
policies before the application is switched to mainnet.

### [HIGH] JUPA-007: Eight high transitive dependency advisories remain

**Confidence:** 9/10
**Category:** Software supply chain

The latest installed Circle wallet/Solana dependency graph retains advisories
in `undici`, `@grpc/grpc-js`, and `toml`. They are transitive rather than direct,
but the affected browser/server paths must be upgraded, overridden only after
compatibility testing, or removed from the production bundle.
